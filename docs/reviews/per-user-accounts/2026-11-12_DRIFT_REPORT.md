## per-user-accounts.md

- **The explicit multi-user composition root is absent.** The design selects `LH_DEPLOYMENT_MODE=multiuser-web` and calls for `src/runtime/deployment-mode.ts`, `multiuser-config.ts`, and `readiness.ts`; no `src/runtime` tree or deployment-mode selector exists. `config.ts:20-37` still derives one process-global data root and shared chat/graph/study paths, `src/server/stores.ts:20-38` wires one global store set, and `instrumentation.ts:3-8` initializes plugins in the Next.js process. Server components and routes still consume those global services directly, for example `app/page.tsx`, `app/chat/new/page.tsx`, and `app/api/chats/route.ts`.

- **Clerk authentication, account provisioning, and the registry/UID ledger are absent.** `package.json` has no Clerk dependency; there are no sign-in/sign-up pages, Clerk webhook, `src/accounts` modules, internal account records, bootstrap flow, administrator role, lifecycle registry, or UID/GID non-reuse ledger. `proxy.ts:8-23` and `src/server/desktop-access.ts:59-78` retain the host/cross-site browser gate and desktop shared capability rather than per-user authentication. Consequently the designed first-admin assignment, legacy-claim authorization, account disablement/deletion/recovery, sole-administrator transfer, and account-scoped request context are not implemented.

- **The account broker/controller, root helper, and per-account worker runtime are absent.** There is no `broker/`, `src/broker`, or `src/worker` implementation, no private account IPC protocol, no controller-issued subject/account/operation/generation capability, no worker-generation fencing, and no on-demand per-UID worker manager. `Dockerfile:111-124` supplies one `/data` tree owned by `node`, and `docker-entrypoint.sh:12-16` recursively changes the entire data tree to `node:node` then permanently executes the application as that single identity. The current process model therefore cannot provide the designed distinct real/effective/saved UIDs, account-private groups, or kernel-enforced cross-account process isolation.

- **The required Docker isolation and resource deployment model is absent.** `docker-compose.yml:18-32` configures the single shared data volume and provider environment but no account/registry/staging/instance-key separation, read-only root filesystem, designated private work mounts, broker supervision, or multi-user readiness checks. The implementation does not enforce the designed per-account process, CPU, memory, disk, and job limits or global active-account/worker/stream/provider/archive/temporary-storage limits. `src/agent/worker-request-admission.ts:5-17` is a process-global model-request concurrency pool (default eight), not an account worker or an account resource boundary.

- **Agent filesystem access still follows a shared home-directory policy.** `src/agent/tools/fs-shared.ts:179-203` resolves relative paths against `os.homedir()`, and its own comment at lines 179-181 states that the path checks are not protection against a hostile concurrent OS user. `src/server/file-access.ts:9-19` expands configured server/home paths. There is no broker-opened per-account workspace descriptor, no account UID execution boundary, and no separation of an agent-readable workspace from account-private application records as required by the design.

- **Uploads do not persist original files in an account-owned private library.** `app/api/graph/import/route.ts:67-95` buffers each multipart `File`, converts/transcribes it, and lines 139-143 pass text or binary extraction input into the global extraction service; the route does not stream into a root-locked account staging channel or retain the original through a stable file record. The proposed `src/files` library/contracts, `FileStore` port and adapter, private file-library UI, and `app/api/files` routes do not exist. `src/core/ports.ts` ends with the existing entity ports and has no `FileStore`. Portable file IDs, ownership/reference metadata, authenticated per-account original downloads, and archive reference rewriting are consequently absent.

- **Shared and predictable temporary-file behavior conflicts with account-private processing.** PDF rendering uses `/tmp/lh-pdf-<short-path-hash>` (`src/agent/subagents/pdf-ops.ts:331-341`); note transcription uses `os.tmpdir()/lh-import-*` (`src/agent/subagents/extraction.ts:1466-1481`); research downloads use `lh-research-*` (`src/agent/subagents/runner.ts:368-372`); and Claude Code creates `claude-code-cwd-*` and `claude-code-private-*` under the OS temporary directory (`src/agent/claude-code/stream.ts:384-407`). These paths have no account staging/promotion protocol or broker-issued descriptors. The PDF render path is additionally deterministic from the input path. Browser helper processes are launched from the shared server runtime (`src/agent/subagents/headless.ts:170-197`), without the designed account-specific working mounts and identity lifecycle.

- **Provider credentials and provider execution remain global.** `src/store/auth.ts:27-65` stores all API credentials in one `AUTH_FILE`, and `src/server/keys.ts:111-123,219-240` reflects and mutates those values in `process.env`. No shared-versus-personal provider policy, administrator-managed shared defaults, opaque provider capability, unprivileged shared-provider executor, controller-held instance encryption key, encrypted BYOK record, key rotation, running-worker credential update, or configuration-generation snapshot exists. The administrator-only provider APIs and account-provider UI described by the design are absent.

- **Plugins, background jobs, and notifications are process-global rather than account-scoped.** `src/server/plugins.ts:38-103` holds one plugin runtime on `globalThis`, binds it to the global chat/graph/job stores, and initializes one plugin host. `app/api/events/route.ts:13-15` returns the global event stream without an account argument. There is no per-account plugin installation/execution identity, account-scoped event delivery, restored-plugin disabled state, or account fencing during deletion/restore. Existing plugin trust and recovery code therefore does not implement the proposed cross-account boundary.

- **Portable account archives and account replacement are absent.** There is no `src/archive` implementation, account export/import route, archive UI, full/chat-only/graph-only manifest, portable dependency plan, passphrase encryption, KDF bounds, staged validation/migration, or archive round-trip support. The existing notes/graph import is an extraction pipeline, not the specified account archive restore. Full-generation durable pointer switching, startup reconciliation, category replacement journaling/rollback, immutable root-controlled export snapshots, quiescence of plugin sidecars/streams/writes, and crash/failure recovery for account replacement are not implemented.

- **Legacy shared-data claim and repair are absent.** Existing `LH_DATA_DIR`/`LH_AUTH_FILE` configuration continues to expose the shared stores directly; no legacy quarantine, all-or-nothing inventory/claim, external-reference validation/copy, non-destructive journal, failure-code/count UI, or host-only repair CLI exists under `src/legacy` or the account routes.

- **The multi-user security and release evidence does not exist.** None of the named deployment, registry, Clerk, broker, isolation, upload ownership, provider isolation, archive, legacy-claim, or all-routes account-scope test files is present. `scripts/smoke-multiuser.mjs`, `docs/multiuser-security.md`, and `docs/account-archives.md` are also absent. There is therefore no current test evidence for effective per-account kernel credentials, cross-account denial, shared-key concealment, immutable snapshots, crash-safe restore, or desktop compatibility under the new explicit mode.

- **The approved review remediation is not yet reflected in the design target itself.** `goldfish_review_report.md` remains `pending resolution`; its 22 proposed edits have not been applied to `docs/designs/per-user-accounts.md`. Thus the checked-in design still contains the first-public-registrant bootstrap, web-owned registry wording, broad root broker, non-crash-atomic multi-directory replacement, account-owned snapshots, every-cache/temp archive scope, and other issues recorded in `critic_report.md`, `comprehension_report.md`, and `zoom_out_report.md`. This is pending design remediation, separate from the not-yet-started production implementation.
